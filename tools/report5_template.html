这一步踩过的坑

  • “带我去椅子那里”，它却开回了出发点模型用了只能去命名地点的 go_to。在提示词里写清楚“去物体那里要用 find_object，go_to 只去 home、north 这类地点”后修好。
  • “蓝色的箱子”被说成认不出提示词加了就近对应的例子（箱子 → suitcase），并要求意思接近时选最接近的类别。
  • 免费模型偶尔返回 429“访问量过大”加了自动重试，依次等 2、4、8 秒。
  • 测试本身写错了“有没有蓝色的箱子”，模型查记忆回答“有”，原本被判为失败。其实查记忆和直接去找都合理，改成两种都算对。
  • 小模型偶尔不听话21 次里有 1 次把“钥匙”偷换成了“遥控器”；实测里它拒绝找钥匙是对的，但还是把 80 个类别全念了一遍，尽管提示词写了“不要列出”。提示词约束不了 100%，所以代码里对每个参数做校验，关键约束不能只靠模型自觉。换更强的 GLM-5.3 可能改善，那是收费模型，还没测。
  • 同一把椅子，这次是“黑色”上一轮看到 20 次判为蓝色（椅垫），这次只看到 3 次、角度不同，判成了黑色（框架）。颜色判断受视角和光照影响，看到次数少时不可靠；“找蓝色椅子”这时就会找不到。

面试题：中英双语参考答案

先自己用中文讲一遍，再对着英文版练。点开看答案。

1. 为什么让 LLM 调用“工具”，而不是直接输出坐标让机器人去？
中文要点
LLM 没见过地图，编出来的坐标可能在墙里；它擅长的是理解人话。所以分工是：LLM 只负责理解意图、从固定选项里选工具和参数，真正的定位、规划、避障由经过测试的 ROS 程序完成。这样出错时也容易定位是“理解错了”还是“执行错了”。
English
The language model has never seen the map, so a coordinate it produces could be inside a wall. What it is good at is understanding the request. So I split the work: the model only interprets intent and chooses a tool with arguments from fixed options, and tested ROS components do localization, planning and obstacle avoidance. It also makes failures easy to attribute: either the model misunderstood, or the robot failed to execute.
2. 工具参数已经写了可选范围，为什么代码里还要再校验一遍？
中文要点
Claude 有 strict 模式，能保证参数一定在范围内；智谱这类接口没有这个保证，模型可能编一个不存在的物体名，或者给出格式坏掉的 JSON。所以每次调用工具前，代码按同一份枚举校验；不通过就把错误信息回传给模型，让它改正或者向用户解释，机器人不会动。原则是：关键安全约束放在代码里，不只靠提示词。
English
Claude has a strict mode that guarantees arguments match the schema, but other providers such as Zhipu don't, so the model could invent an object name or return malformed JSON. Before every tool call I validate the arguments against the same enums. If validation fails, the error goes back to the model as the tool result so it can correct itself or explain to the user, and the robot never moves. The principle: critical constraints live in code, not only in the prompt.
3. 你怎么评测 LLM 部分的效果？为什么每句话要测好几次？
中文要点
分两层。第一层用“假机器人”只测语言理解：一组典型指令，检查模型选的工具和参数对不对，又快又不花钱。第二层是端到端：真仿真、真模型，再用 Gazebo 里的真实位置确认机器人确实停在物体前面。模型输出有随机性，同一句话结果会变，所以每句测 3 次，看通过率而不是看一次的结果。评测标准也要允许多种合理做法，我就遇到过把正确行为判成失败的情况。
English
I evaluate at two levels. First, a language-only probe with a fake robot: a set of typical requests, checking that the model picks the right tool and arguments. It's fast and free. Second, end-to-end tests in the simulator with the real model, where I check the robot's ground-truth position in Gazebo to confirm it actually stopped in front of the object. Model outputs vary between runs, so I repeat each request three times and report a pass rate. The grading also has to accept every reasonable behaviour; I once had a test that marked a correct answer as a failure.
4. 调用大模型 API 时，遇到“太忙”或网络错误怎么处理？
中文要点
先区分能不能重试：429（太忙、限流）和网络超时可以等一会儿再试，我用指数退避，依次等 2、4、8 秒；401（key 错误）这种重试也没用，直接给出清楚的提示。机器人这边的错误（比如导航服务没启动）不让程序崩溃，而是作为工具结果告诉模型，由它用人话解释给用户。
English
First I separate retryable from non-retryable errors. A 429 rate limit or a timeout can be retried, so I use exponential backoff: wait 2, 4, then 8 seconds. A 401 means the key is wrong and retrying won't help, so the program prints a clear message instead. Errors on the robot side, such as the navigation server not running, don't crash the program; they go back to the model as the tool result, and the model explains the problem to the user in plain language.
5. 为什么把 LLM 做成可以替换（智谱 / Claude）？
中文要点
对话循环和机器人接口只写一份，每家模型一个“后端”，负责自己的消息格式（智谱用 OpenAI 风格的 role: tool，Claude 用 tool_result 块）。换模型只改一个参数，机器人这一侧完全不动。好处是可以按成本、速度、地区和合规要求选模型，也方便对比不同模型的效果。
English
The tool loop and the robot interface are written once, and each provider gets a small backend that handles its own message format: Zhipu uses OpenAI-style messages with role "tool", while Claude uses tool_result blocks. Switching models is one command-line flag, and nothing on the robot side changes. That lets me choose a model by cost, latency, region or compliance needs, and compare models on the same tests.
